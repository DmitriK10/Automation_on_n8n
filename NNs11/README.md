## Стратегия обновлений

Обновление делаем только по причине, а не потому что вышла новая версия.
Причин две: нужна функция или исправление, которое мешает работе; закрыта дыра
в безопасности.

Когда **не** обновляемся:

| Ситуация | Почему |
|---|---|
| идёт активная работа, через сценарии проходят заявки | обслуживание — только на простое |
| нет свежего бэкапа | откатываться будет некуда |
| версия вышла вчера-позавчера | ждём 1–2 недели, пока накопятся чужие ошибки |

Исключение одно — критическое обновление безопасности. Но и тогда сначала
бэкап.

## Чтение changelog: четыре фильтра

1. **Затронуты ли ноды, которыми я пользуюсь?** На стенде `Schedule Trigger` не
   используется ни в одном сценарии — значит изменение планировщика в 2.45 нас
   не касается.
2. **Есть ли изменения по безопасности?** Смотрим разделы security и breaking
   changes, не пропускаем.
3. **Мне это надо?** Ищем функции под свои задачи, а не всё подряд.
4. **Какой тариф нужен?** Пометка Availability = Business/Enterprise означает,
   что строить на функции нельзя.

Дополнительно: пометка **Preview** (например Agents в 2.40, n8n Assistant в
2.35) — не для продакшна, поведение может измениться.

Источники: `docs.n8n.io/changelog` (раз в месяц и перед обновлением),
Release Notes (детали по релизам), GitHub Releases (когда нужен конкретный
коммит).

## Версии: полезные команды

```bash
# узнать текущую версию
docker exec n8n-lab n8n --version

# что доступно в npm
docker exec n8n-lab npm view n8n version      # последняя стабильная
docker exec n8n-lab npm view n8n dist-tags    # latest / beta / next / rc

# закрепить версию (Docker)
docker pull n8nio/n8n:2.29.8

# закрепить версию (npx)
npx n8n@2.29.8
npx n8n@latest        # то же, что просто npx n8n

# попробовать версию на отдельной папке и порту
N8N_USER_FOLDER=./restore-test N8N_PORT=5680 npx n8n@2.29.8
```

`npx n8n` без версии каждый раз подтягивает последний релиз — на учебной машине
это нормально, для продакшна нет.

## Порядок обновления

```
бэкап → обновление → проверка → логи
```

Проверка — не «интерфейс открылся», а:

- открыть основные сценарии;
- проверить подключения (credentials);
- запустить ключевые автоматизации;
- пропустить тестовую заявку через весь процесс до конца.

Между «система открылась» и «система работает» — большая разница. Обновление
ломает не запуск n8n, а отдельные ноды.

Важное дополнение из урока 10: бэкап снимаем транзакционно (`.backup`), потому
что база в режиме WAL. Копия, сделанная обычным `cp`, окажется без последних
записей.

## Сброс пароля администратора

Кнопки «Забыли пароль» без SMTP нет. Поддерживаемый способ один:

```bash
# Docker
docker exec -it n8n n8n user-management:reset
docker restart n8n

# npx
N8N_USER_FOLDER=~/restore-test npx n8n user-management:reset
```

**Команда необратима и не спрашивает подтверждения** — бэкап делаем до неё.
Для Docker рестарт обязателен, иначе сброс не вступит в силу.

После сброса открываем инстанс, создаём нового владельца (почта может быть
любой) и проверяем, что сценарии и подключения на месте.

### Что проверено на одноразовой копии

Сброс выполнялся на копии базы из урока 10, отдельный контейнер на порту 5690.
Рабочий инстанс на 5678 не затрагивался.

| Что считаем | До сброса | После сброса |
|---|---|---|
| Сценарии | 9 | 9 |
| Подключения | 8 | 8 |
| Запуски | 50 | 50 |
| `pragma integrity_check` | ok | ok |
| Владелец | 1, с почтой | 1, без почты и пароля |

После сброса `showSetupOnFirstLoad: true`, владелец регистрируется заново, вход
новым паролем работает, данные на месте.

## Грабли, которых нет в тексте урока

| Что видно на практике | Как правильно |
|---|---|
| `user-management:reset` не удаляет строку владельца, а обнуляет почту, имя и пароль | для одного владельца результат тот же, но формулировка «удаляет учётные записи» неточна |
| чтение базы снаружи контейнера показывает устаревшие числа | база в WAL: копировать вместе с `-wal` и `-shm` либо останавливать контейнер |
| `/setup` и `/signin` отвечают 404 сразу после `healthz 200` | `healthz` отвечает раньше веб-интерфейса; после старта нужно дать время |
| команда сброса срабатывает без подтверждения | бэкап обязателен: отменить нельзя |
